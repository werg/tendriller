# Build or connect a Tendriller application

Start with `tendril_guide` (`topic: "start"`), then `topic: "build"`, `topic: "capabilities"`, and `topic: "delivery"`. Use `topic: "connect"` for an existing application, `topic: "sensors"` for capture consent, `topic: "oauth"` for outbound OAuth/org tie-ins, `topic: "pricing"` / `topic: "self_hosting"` for plan headroom or self-hosting, `topic: "changelog"` for notable changes & sunsetting notices, and `topic: "deployment"` only for an explicitly requested rollout. When returning to a fallow workspace (or seeing active notices), call `get_broadcasts` / `tendril broadcasts` and `tendril changelog` (or `tendril_guide` `topic: "changelog"`) before editing. The tool returns maintained instructions and the selected `serviceOrigin`; keep every setup and discovery route on that exact origin, including staging. If absent, inspect `get_profile`/`list_tendrils` fields `setup.startHere`, `setup.buildGuide`, and `setup.discoveryUrl` and refresh the catalog; never infer production from a name or switch service origins. An empty application list does not mean creation is unavailable.

Before downloading/installing, read the exact service origin's `/api/service`, `/.well-known/tendriller.json` and `/api/readiness`. Require same-origin `mode:"open"` and `creation.available:true`. Otherwise stop and report its next action. Use the immutable `firstApp.release` kit, matching SDK/tools/**authority**/session archives, source/tree/hash composition and exact lockfile—not private kernel imports or mixed same-version builds.

## Register the agent, create, initialize, publish, then admit the browser

One agent (one `ta_` credential, one signing key, one wrap key) maintains every page it creates from one retained starter workspace. For linked-account registration, run `npx tendril workspace key --service SERVICE_ORIGIN --handle HANDLE` in the workspace and call `register_agent` with its printed public `handle`, optional `bio`, `publicKey` and `wrapKey` under this connector's existing grant. The host derives the verified owner; OAuth credentials never enter the workspace and the private keys never leave it. Save the result privately and run `npx tendril workspace adopt --service SERVICE_ORIGIN --credential FILE`, then `npm run page:new -- <slug>`; further pages reuse the agent. An existing page needs the owner's explicit per-agent grant on the dashboard, then `npx tendril page grant <slug> <page-id>`. Calling `register_agent` again with the same name rotates the token; adopt the newest result and never fall back to anonymous registration. Without a linked account, `tendril workspace init --owner EMAIL` or a dashboard join code (`workspace join`) registers the agent.

Prepare early and publish the full signed UI before owner sign-in. `npm run init -- <slug>` prepares the publisher policy (signed by the workspace's one opaque shared signer, not a per-page key) and creates the page keys with the agent as creator: signed descriptor, genesis membership pinning the owner account and host attestation key, and the first epoch key, recorded by `initialized.json` (`--browser-first` leaves creation to the owner's first browser). `npm run deploy -- <slug>` publishes. Start `npm run agent`, then give the person the ready page URL and any separately prepared tool-consent URL without waiting for a “claimed” reply. They complete their own sign-in.

The host attests the signed-in browser's device key and wrap key for the owner account; any online member (the agent program or an admitted device) admits it into signed membership and wraps the keys to it. The host never signs membership or sees epoch keys. Until a member is online the browser shows that it is waiting. Additional devices, strict-mode approval and invites for other people use the same admission; Remove device rotates the key. Retained identity/authority/keys/data reopen before background host refresh/discovery. Membership does not overwrite SQL collective/object/row/column permissions. There is no ordering pause, selected-generation transition or compatibility path.

## Authoring, reactivity and optional finality

Ordinary offline-first apps default to finality `none`. Canonical order is solely signed author timestamp, signing key bytes and stable proposal-ID bytes. Submission acknowledges exact durable local storage, not remote execution. Distinguish **stored**, **materialized locally (revisable)**, **retained by peers**, **finalized**, and **excluded**. Preserve original IDs/time/bytes after uncertainty; inspect/retry the retained original, never silently retimestamp.

Save depends on local signer/storage/key prerequisites, not peers, a successful current/global read, native tools or a finalizer. Finality is optional inclusion/author-time closure evidence, never a sorter. Configured policy is not demonstrated provider availability. A closed frontier can exclude genuine unseen offline work behind it; explain this tradeoff and retain excluded originals. No-finality final waits explicitly fail as unsupported. Provisional claims do not establish global exclusivity or authorize irreversible external effects.

SQL schema, DML and permissions are ordinary authorized atomic transactions. Engine/platform manifests do not freeze database schema or require code publication for ALTER/CREATE/DROP. Existing consumer/tool/column approvals never silently expand after schema changes.

Build real domain views: stable-ID lists/details, inspectors, reviewed edits and mobile navigation, not a JSON editor. Render coherent materialized snapshots plus separate local drafts/view state. Notifications invalidate/rederive; never append arrivals into another UI database. Late earlier operations can revise outcomes, rows, counts and schema. Missing-table/query errors mark the last snapshot not current without erasing unsent input or blocking unrelated local authoring.

## Verify rather than assume

Use existing device-local owner/root locks and direct-first RTC/two-lane encrypted relay helpers. Do not introduce another selector, always-failing RTC stub or app backend. Qualify actual authenticated data traffic/direct versus forced fallback. The agent program (`tendril agent run`: one hub connection, one session per initialized page) and tool providers are optional independently authorized processes; if used, report actual lifetime/private-state resume details. Their absence must affect only their features.

For page requests to the same conversation, during a turn or while idle, read `tendril_guide` with `topic: "conversation"` (or the same-origin `/docs/CONVERSATION_DELIVERY.md`). Inspect the current host's subscription or exact existing-thread execution mechanism, authentication and owner-approved event. Use its retained thread binding and per-page handled checkpoints; never choose the latest thread or a new agent per page as a substitute. For Codex, inspect current thread state: use the verified steering route for an active turn and queue/resume for idle or unloaded state. Plain `codex queue` waits while a turn runs and does not satisfy active delivery. Respect explicit interruption. Verify a request injected into the same active turn before completion, then a request after the turn ends and another after the answering turn ends, with durable receipts and answers. A missing subscription tool, reauthentication or refused thread admission leaves that stage unqualified; retain pending requests. A connected page owner, event forwarder or mounted card alone does not establish future conversation wake.

For apps with a request consumer, verify worker-owned ephemeral presence and request/receipt/answer behavior only through its declared capabilities (`/docs/AGENT_REQUESTS.md`); report missing support instead of inventing commands. Bind presence to the actual handler's lifetime and implemented topics, select its peer, `consumerId` and request topic in the browser, stop only that worker while the native participant remains connected and confirm the assistant becomes stopped/stale. A stored or materialized operation does not establish that an agent read the request.

Exercise owner sign-in admitted by the running agent; real local command/materialization; complete-graph offline acknowledgment, CRUD and reload; second-profile admission and Remove device; convergence and separate retention; late earlier state/schema changes; and signed publication. Run the dedicated second pass from `delivery` at desktop and **320px**, fresh profiles, every main flow, Back/deep links, keyboard/focus, long content and loading/empty/stale/error states. Retain before/after screenshots. Transport/persistence checks alone are not UX completion.

## Optional tools, account linking and sensors

For an existing app, use `list_tendrils` then `describe_application` (which includes live `sqlSchemas` for every `chronolog/sql` topic plus `permissionsSummary`). Use `query_application`, read-only `query_sql`, or parallel `query_multiple_applications` across up to 8 opted-in pages — zero separate `domain.js` bundle is needed. Existing participants propose only declared operations; the owner reviews exact queries/commands/events. Preserve independent consuming-agent approval and tool-provider idempotency. Do not silently replace the app or expand rights. When a page uses zero-OAuth public (`openMembers`) or M-of-N (`multisigMembers`) governance instead of default private OAuth E2EE, surface clear security UX (`shared/helpers/governance.mjs`) so the user always knows whether data is public or encrypted. Query/write responses carry revisable operation/snapshot facts. Event consumers must understand resets/retractions and finalized versus provisional evidence.

Follow the person's normal account-linking prompt; credentials/codes stay out of chat. Ordinary calls use the existing OAuth-client binding. Separate proof bindings are for independently revocable agents, not a mandatory new identity for every call. Missing native/provider runtime is a named prerequisite for those optional tools, not browser data use.

For sensors read `topic:"sensors"`. Inspect only relevant capabilities; use standard browser APIs, existing content/signals/commands and tracked asynchronous cancellation. An agent observation request displays a prompt only. A trusted local gesture starts capture; explicit consent/review authorizes sharing/retention. Missing inference disables analysis, not ordinary edits.

For restart, consult same-origin `/docs/AGENT_RESTART.md`; reconnect attach clients to the restarted agent program, preserve retained profiles, snapshot-aware cursors and original pending inputs. A live page, optional MCP socket or inbox does not guarantee future conversation wake. Report the process actually running, exact tests and unverified boundaries. Users revoke account access at `/oauth/connections` or app tool scopes at `/connections` on the same service origin. Use `topic:"troubleshooting"` for the exact next action; no automatic storage wipe or unrequested deployment is authorized.
